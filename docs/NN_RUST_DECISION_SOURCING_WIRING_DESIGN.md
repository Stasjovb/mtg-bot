### 1.2 The codec seam: `action_encoding.py`

`src/mtg_bot/training/action_encoding.py` is the fixed-vocab codec
mapping engine `Decision` objects ↔ policy-head slot indices
(`ACTION_VOCAB_SIZE = 517`, `:254`). The three public ops:

- `encode(decision, state, viewer, version)` (`:505`) — Python
  `Action` object → slot int. Operates on
  `eng = _engine_state(state)` (`:527`) where `_engine_state` is
  `getattr(state, "engine_state", state)` (`:316-319`) — i.e. it
  reads the **Python** `GameState` zones (`eng.player_by_id(viewer)
  .hand` etc., `:383/:393/:403/:410/:482`). It dispatches on Python
  `Action` types: `PassPriority`/`PlayLand`/`CastSpell`/
  `ActivateAbility`/`ActivateStation`/`TurnFaceUp`/`UnlockRoomHalf`
  imported from `mtg_bot.actions` (`:128-131`), plus
  `AttackerDecision`/`BlockerDecision` from `search.combat_decisions`
  (`:135`).
- `decode(slot_idx, state, viewer, version)` (`:750`) — slot int →
  Python `Action` object, built from positions in the **Python**
  engine zones (`:779 hand[pos].id` etc.).
- `legal_action_mask(state, viewer, version)` (`:1020`) — bool array
  of `ACTION_VOCAB_SIZE`. Calls `_enumerate_legal(state, viewer)`
  (`:1057`) → for the priority window prefers
  `state._legal_actions_cached(viewer)` (the adapter's cached
  `legal.legal_actions`, `:1122-1126`) and honours every adapter
  short-circuit (`_should_skip_*`, `_can_short_circuit_to_pass`,
  `_should_force_landdrop`, `:1108-1138`), else falls back to
  `legal_actions(eng, viewer)` directly (`:1126`).

The codec is **Python-engine-shaped end to end**: it consumes/produces
`mtg_bot.actions.Action` instances and indexes Python `GameObject`
zone positions. It carries the `positional_v1` / `canonical_v2`
version axis (`:74-104`, the project `CLAUDE.md` "Action encoding
versions" contract); `_canonical_zone_sort_key` (`:347-370`) sorts
hand/gy/exile by `(printing.name, warped, cast_via_warp, face_down,
…, card.id)` under v2. **This versioning is independent of the
flip** and survives unchanged (§3.2).

### 1.4 How the cross_engine harness sources the action today (the contract that inverts)

`src/mtg_bot/parity/cross_engine.py` is **Python-drives /
Rust-mirrors**: a `decision_selector(py_state, rust_state, step)`
computes an `action_dict` **from the Python state** (the SoT), then
`step_both(py_state, rust_state, action_dict)` (`:10305`) replays the
*same* dict on BOTH engines: `py_apply_action(py_state, actor,
_dict_to_python_action(action_dict))` (`:10333,:10364`) AND
`rust_state.apply_action(action_dict)` (`:10365`), then
`compare_fields(py_view, rust_view)` (`:10386`). The default selector
is `_default_pass_priority_selector` (`:10498`); `walk_both`
(`:10440`) runs the loop. The harness *never* reads
`rust_state.legal_decisions()` to choose — verified `:10443-10448`
("PassPriority is the only action both engines can drive trivially
without needing legal-action enumerator parity … that's the next
slice's parity surface"). There is exactly one direct
`rust_state.legal_decisions(0)` *probe* in the tree
(`cross_engine.py:13660`, the CE17 defender-filter assertion) — a
diagnostic, not a decision source.

**The flip inverts this contract**: post-flip the NN/MCTS sources the
decision set from `rust_state.legal_decisions(pid)` and applies via
`rust_state.apply_action(dict)`; Python (if present at all) runs as a
*shadow checker*, not the driver. B3 is the wiring for that inversion.

### 2.2 Output shape of `legal_decisions` and how it maps to the codec slots

`rust_state.legal_decisions(pid)` returns a `list[dict]`; each dict is
the SAME shape `actions.rs:action_to_pydict` produces and
`parse_action`/`apply_action` accepts (`state_ops_legal.rs:1149-1151`,
e.g. `{"kind":"cast_spell","id":7,"use_warp":False,"kicked":False,
"cast_for_free":False,"use_impending":False,"cast_room_half":None}`
— the 6-key shape, `:135-141`; `{"kind":"play_land","id":42}`;
`{"kind":"activate_ability","source_id":id,"ability_index":0}`;
`{"kind":"declare_attackers","attacker_ids":[…]}`;
`{"kind":"declare_blockers","assignments":[[b,a],…]}`;
`{"kind":"pass_priority"}`).

The codec (`action_encoding.encode/decode`) consumes/produces Python
`mtg_bot.actions.Action` **objects**, NOT dicts. The existing
dict→Action converter is `cross_engine._dict_to_python_action`
(`:10079-10177`) — but that symbol is **classified VESTIGIAL** by
`BRIDGE_VESTIGIALIZATION_PLAN.md` §2.2 (it is part of the
reverse-serialization path retired at Step 6). **B3 must therefore
own a small, NON-vestigial Rust-dict ↔ codec adapter** (§3.2) rather
than depend on a Step-6-doomed symbol. The mapping is mechanical
because the dict `kind` + ids map 1:1 to the codec's slot families
(`action_encoding.py:19-43` taxonomy): `pass_priority`→`SLOT_PASS`;
`play_land`→`LAND_FROM_{HAND,GY,EXILE}` by zone-position of `id`;
`cast_spell`→`CAST_FROM_{HAND,GY,EXILE}[pos][variant]` where the
variant is derived from the dict's `use_warp/kicked/cast_for_free/
use_impending/cast_room_half` flags exactly as
`_cast_variant_for_hand` (`:423-455`) reads the `CastSpell`
dataclass; `activate_ability`→`ACTIVATE_ABILITY[bf_own_pos][ability_
index]`. The position lookup still indexes the **viewer's zones** —
post-flip those positions must be read from the **Rust** state's
zones (§3.3), not the retired Python `GameObject` lists; the
canonical_v2 sort key (`:347-370`) maps onto Rust object attributes
1:1 (printing name + the same boolean modifier flags + object id),
which §3.2 specifies precisely.

  creature at a time, `engine_adapter.py:808-828`, and finalizes,
  `:1101-1144`). Sourcing combat decisions from Rust's powerset would
  (a) lose the progressive-widening per-creature MCTS shape the codec
  + tree are built for (`action_encoding.py:62-65,:39-42`
  ATTACKER/BLOCKER slots are *factored*), and (b) silently drop the
  middle of the combinatorial space above the cap (`state_ops_legal.rs:
  246-256/391-399`), so the Rust-sourced combat decision set is
  **neither a superset nor byte-equal** to the Python factored set.
  **Scope:** the Rust counterpart of the C1 work for the *combat
  axis* — a Rust factored per-attacker / per-blocker emission
  (mirroring `search/combat_decisions.py:44-55/120-178`) replacing
  the powerset/product block (the `state_ops_legal.rs` docstrings
  themselves anticipate this: *"a future factored-search slice
  replaces this"*, `:243-247/:391-399`). This is **a new sibling
  Rust slice ("rust-legal-decisions-factored-combat"), NOT B3-impl
  itself** — B3 (the wiring) is HARD-BLOCKED on it exactly as B3 was
  blocked on C1. It is the C1-analog for combat. Estimated 1 Rust
  slice (the eligibility loops already exist and are
  defender/sickness-correct, `state_ops_legal.rs:1194-1223`; the work
  is changing the *emission shape* from powerset to one factored
  dict per pending creature + the apply-side accumulation, which the
  Rust `apply_action` `DeclareAttackers/Blockers` arm already accepts
  as the finalized whole). **This is the precise hidden gap the spec
  was commissioned to surface.**
- **G2 — PlayLand per-turn-limit divergence (bounded, accepted, NOT
  a blocker).** Rust over-offers a 2nd PlayLand (no
  `lands_played_this_turn` field; `state_ops_legal.rs:48-58`,
  SL-documented). Direction is "Rust offers one extra structurally;
  apply rejects it" — it can pollute the *root legal mask* with a
  slot the engine then refuses, a mild self-play-data smell but NOT
  the un-payable-cast class C1 fixed (apply is the hard gate). Scope:
  a tiny Rust follow-up (add the field + gate, the SL note's "Phase 5
  fix") OR a B3-side mask filter (mirroring the existing
  `_should_force_landdrop` adapter-filter pattern,
  `engine_adapter.py:836-838`). **Recommend: B3-side mask filter in
  the provider (§3.1) as the parity-safe interim, with the Rust field
  as the proper fix sequenced post-flip.** Not flip-gating.
- **G3 — mid-resolution `Resolution*` decisions have no Rust emission
  (architectural, scoped, accepted-via-determinism).** Python's
  engine pauses mid-resolve for agent callbacks (target/X/mode/…)
  and the adapter exposes them as search nodes
  (`engine_adapter.py:840-882`). Rust resolves atomically with
  push-time/no-agent seating (`state_ops_resolve.rs:657-662`) — there
  is no callback-pause surface, so `Resolution*` decisions simply do
  not exist in a Rust-sourced game. **This is NOT a "Rust emits the
  wrong set" defect — it is "Rust makes these choices internally,
  deterministically, by the same rules the Python resolve arm uses"**
  (the C1 Slice-2 target work explicitly used "the SAME
  `bf_iter_etb_sorted` object filter the matching resolve arm uses —
  single source of truth", `SEARCH_LIMITATIONS.md:5718-5727`). The
  consequence: post-flip the search tree loses the mid-resolution
  decision *nodes* — the bot no longer searches over e.g. which
  target to pick; Rust picks deterministically. **Disposition:** this
  is an explicitly **accepted staged-flip consequence** in the same
  family as the §1.1/§7-OQ3 reduced-card-universe acceptance —
  documented, C6-fenced (the admitted cards' resolve arms are the
  byte-equal-pinned ones), and recorded as a new
  `docs/SEARCH_LIMITATIONS.md` entry at B3-impl landing ("post-flip
  the search no longer factors mid-resolution sub-decisions; Rust
  resolves them deterministically by the pinned resolve-arm rules").
  It is **NOT a hard flip-blocker** (the determinization is
  rules-correct on the admitted set) but it **IS a strength caveat**
  the umbrella's flip judgment must see — flagged here, owner =
  the umbrella's flip go/no-go. A *future* enhancement (a Rust
  agent-callback surface mirroring the resolution channel) is a
  large, separate, post-flip project — explicitly out of B3 scope.

> **Verify-first correction (name vs code).** One might assume
> "C1 closed `legal_decisions == legal_actions`, so the Rust set is
> drop-in for the whole search." **It is not** — C1's contract is
> precisely scoped to the *CastSpell* set on the live cast surface
> (`SEARCH_LIMITATIONS.md:5696-5703`). The combat axis (G1) and the
> mid-resolve axis (G3) were never in C1's scope. Reading only the
> "C1 COMPLETE" headline and wiring B3 to source ALL decisions from
> Rust would silently ship G1's broken combat shape into self-play.
> This is the exact mis-classification this spec exists to catch.

## 3. The wiring design

### 3.1 A Rust-engine-backed decision/apply provider behind the existing seam

**Design principle: MCTS/ISMCTS/PIMC/the codec/the NN are UNCHANGED.
Only the adapter's 8 Protocol methods change which engine they
query.** Introduce a **second concrete `search.protocol.GameState`
implementation** living beside `MtgGameStateAdapter`:

`RustGameStateAdapter` (new module `src/mtg_bot/search/
rust_engine_adapter.py`, B3-impl owns it). It implements the SAME
Protocol (`protocol.py:42-99`) — search cannot tell the difference —
but its internals drive the Rust `#[pymethods]` surface (§2.1):

| Protocol method | Rust-backed implementation |
|---|---|
| `clone()` | wrap `self._rust.clone()` (`state.rs:1689`) + copy adapter-side priority/combat bookkeeping (same fields `MtgGameStateAdapter.clone` copies, `engine_adapter.py:688-751`) |
| `legal_decisions()` | `dicts = self._rust.legal_decisions(self._priority_pid)`; for the **priority window** return them mapped through the §3.2 dict↔Decision adapter; for the **combat window** return the §3.3 factored shape (DEPENDS ON G1's Rust factored-combat slice); apply the §2.4-G2 PlayLand per-turn mask filter + the existing heuristic short-circuits (port `_should_*` from `engine_adapter.py:344-656` — they read step/stack/priority which the Rust state exposes) |
| `apply(decision)` | map Decision→dict (§3.2) then `self._rust.apply_action(dict)`; run the priority-loop body against Rust (`self._rust.resolve_top_of_stack()` / `apply_sbas()` / `stack_size()`, the §2.1 drain primitives `cross_engine.py:10298-10300` already uses) — a Rust-side port of `engine_adapter.py:945-988 _run_priority_action` |
| `active_player()` | from Rust priority/active/defender (the §2.1 priority extraction); combat-phase tag handled adapter-side as today |
| `is_terminal()` | `self._rust.is_over()` |
| `winner()` | `self._rust.winner_id()` |
| `players()` | fixed `[0, 1]` (2-player model, same as Python) |
| `chance_outcomes()` | `[]` (unchanged, §3.4) |

The provider preserves the adapter's *reimplemented priority loop*
design (`engine_adapter.py:18-21`) — the loop logic is Python, only
its engine calls become Rust. The factored-combat phase machinery
(`_combat_phase`, `_pending_attackers`, `engine_adapter.py:808-828,
1080-1144`) is **reused verbatim** once G1's Rust factored emission
lands (it feeds the same accumulate-then-finalize-to-whole-action
shape `rust_state.apply_action({"kind":"declare_attackers",…})`
accepts).

**The single atomic-revert flag.** Per the umbrella's rollback
constraint (`SOT_FLIP_CUTOVER_PLAN.md` §3 "the decision-source and
SoT-designation switches MUST be a single (or two coupled) flag(s) so
revert is atomic — a half-reverted state must be unrepresentable"):
one config knob `decision_source: Literal["python", "rust",
"rust_shadow"]` (B3-impl puts it on the existing
`HeuristicsConfig`/`NNPimcConfig` construction sites — the four
`NNPimcConfig` sites in `training/distributed.py` the project
`CLAUDE.md` documents, plus `data_gen.py:851`/`self_play.py:534`
adapter construction). `python` = today (default until flip);
`rust_shadow` = §4 bake-in (Rust drives, Python checks); `rust` =
post-bake-in (Rust only). The wrap-site is the ONE place `MtgGame
StateAdapter(...)` is constructed → a factory chooses the
implementation. Revert = flip the one enum back. Half-reverted is
unrepresentable because the enum is read once at game-construction and
the whole game uses one provider.

### 3.2 The action-encoding codec mapping (Rust dict ↔ fixed policy slot)

The codec stays Python-`Action`-shaped and **version-unchanged** (the
`positional_v1`/`canonical_v2` axis, `action_encoding.py:74-104`, is
orthogonal to the engine choice). B3-impl adds a thin,
**non-vestigial** bidirectional adapter (NOT `cross_engine.
_dict_to_python_action`, which Step 6 retires — §2.2):

- `rust_dict_to_decision(d: dict) -> Decision` — `kind` dispatch to
  the codec's `Action` constructors (`PassPriority()`,
  `PlayLand(card_id=d["id"])`, `CastSpell(card_id=…, use_warp=…,
  kicked=…, …)` exactly the 6-key shape `state_ops_legal.rs:135-141`
  emits, `ActivateAbility(source_id=…, ability_index=…)`). For
  combat, the §3.3 factored shape. This is the inverse of the codec's
  own `decode`-time `Action` construction (`action_encoding.py:
  774-802`) — same `Action` classes, fed from a Rust dict instead of
  a Python slot.
- `decision_to_rust_dict(decision: Decision) -> dict` — the inverse,
  for `apply`. Mirrors `actions.rs:action_to_pydict`'s key shape so
  it round-trips through `rust_state.apply_action`.

**Slot mapping (the load-bearing detail).** The codec indexes a
card's *position within the viewer's zone* (`_find_card_zone`,
`action_encoding.py:468-497`; `_hand/_graveyard/_exile`,
`:373-406`). Today those positions come from the **Python**
`eng.player_by_id(viewer).hand` (`:383`). Post-flip the position
source must be the **Rust** state's zone for that viewer. Two
options, with a verify-first recommendation:

1. **Recommended: a Rust zone-listing pymethod returning the
   viewer's hand/gy/exile object ids + the canonical_v2 sort tuple
   fields** (printing.name + the 7 boolean modifier flags
   `_canonical_zone_sort_key` reads, `:361-369` — Rust already has
   `printing` + per-object `warped`/`face_down`/etc.). The codec's
   `_hand`/`_engine_state` helpers get a Rust-state branch that lists
   from this method instead of `player_by_id().hand`. **This keeps
   the codec's slot semantics bit-identical** (same positions, same
   v1/v2 sort, same `card.id` tiebreaker) — a v-chain-SAFE change
   (trained v17 weights keep working; the slot mapping is unchanged,
   only its data source moves). *NB: this is a small Rust read-only
   pymethod — it is the ONE place B3 needs a Rust addition, and it is
   pure state extraction (no rules logic), classified as a sibling
   Rust micro-slice, not B3-Python-impl.*
2. *Rejected:* deriving positions from the Rust→Python field-view
   reverse projection (`parity_smoke._build_field_view`) — that path
   is Step-6 VESTIGIAL (`BRIDGE_VESTIGIALIZATION_PLAN.md` §2.2), so
   building B3 on it inverts the retirement order.

`positional_v1`↔`canonical_v2` interaction: unchanged. v1 reads raw
Rust zone order; v2 sorts by `_canonical_zone_sort_key` over the
Rust-supplied (name, flags, id) tuple — byte-identical to today's
Python-sourced sort because the tuple fields are 1:1
(printing.name + the same booleans + object id; the Rust object
carries all of them). The cache-key/`slot_fingerprint` machinery
(`mcts._cache_key`, project `CLAUDE.md` "Action encoding versions")
is untouched.

### 3.3 Combat: factored decisions via Rust (DEPENDS ON G1)

The provider's combat window MUST present the **factored**
`AttackerDecision`/`BlockerDecision` shape (the codec's
ATTACKER/BLOCKER slots `action_encoding.py:39-42` and the MCTS
progressive-widening tree are built for it). Two-part:

- **G1 prerequisite (sibling Rust slice):** Rust `legal_decisions`
  gains a factored per-eligible-attacker / per-eligible-blocker
  emission (one dict per pending creature) replacing the
  powerset/product block, mirroring `search/combat_decisions.py:
  44-55/120-178` — the `state_ops_legal.rs` docstrings already name
  this as the planned replacement (`:243-247/:391-399`). The
  eligibility loops are already byte-correct on defender/sickness
  (`state_ops_legal.rs:1194-1223`).
- **B3 provider side:** consume the factored Rust emission exactly as
  the existing `MtgGameStateAdapter` consumes its own
  `AttackerDecision`/`BlockerDecision` enumeration
  (`engine_adapter.py:808-828`), accumulate, and finalize via
  `rust_state.apply_action({"kind":"declare_attackers",
  "attacker_ids":[…]})` — the whole-action shape Rust's
  `apply_action` already accepts (`state_ops_actions.rs:145`, the
  `DeclareAttackers/Blockers` arm). The `_combat_phase`/
  `_pending_*`/`_chosen_*` bookkeeping ports verbatim from
  `engine_adapter.py:1080-1144`.

### 3.4 Determinization / PIMC cloning via Rust + eval-state extraction

- **Determinization.** Today `determinize.determinize` permutes
  `card.printing` on **Python** `GameObject`s in hidden zones
  (`determinize.py:153-157`). PIMC drives it via `sub.engine_state`
  (`pimc.py:381-385`); ISMCTS via `state.engine_state.clone()`
  (`ismcts.py:348-349`). Post-flip the determinizer must permute the
  hidden-zone printings of the **Rust** state. **Verify-first scope
  decision:** determinization is a *hidden-information sampling*
  operation, not a rules operation — it reassigns which printing each
  hidden `GameObject` carries within its owner's pool, preserving
  zones/ids/counts. It needs a Rust pymethod to (a) list hidden-zone
  object ids per the same `viewer_knows` rule
  (`determinize.py:37-61`, over Rust `publicly_known_to`/`zone`/
  `owner_id` — Rust already tracks these for the fingerprint) and (b)
  set an object's `printing_id` (Rust stores `printing_id`, not a
  Python printing ref — `state_ops_legal.rs:1199`
  `self.registry.lookup(obj.printing_id)`). **This is a bounded Rust
  read+write extraction surface (a sibling micro-slice), NOT rules
  logic** — it is the determinizer's data plumbing, same shape as the
  §3.2 zone-listing method. The `_PUBLIC_ZONES` / `viewer_knows`
  *policy* stays Python (it is epistemic-model logic, not rules) and
  is unchanged. PIMC's `samples`/aggregation and ISMCTS's
  particle-filter belief machinery are **entirely unchanged** (they
  operate above the Protocol; the determinizer is the only Rust
  touch).
- **Eval-state extraction.** `extract_features(state, viewer_id)` /
  the structured tokenizer (`nn_evaluator.py:49`) consume the Python
  engine state's structure. Post-flip the features must be extracted
  from the Rust state. **This is the largest single feature-surface
  port and is explicitly OUT of B3's wiring scope** — it is
  `docs/NN_REPRESENTATION_ROADMAP.md` territory (the structured-input
  rewrite). **B3's interim, parity-safe design:** keep feature
  extraction reading a Python-shaped view *materialized from the Rust
  state for the eval path only* — the bake-in (§4) runs Python as a
  shadow anyway, so during bake-in the Python state IS present for
  `extract_features`; for the post-bake-in `rust`-only mode, B3-impl
  routes `extract_features` through the SAME surviving loader-side
  forward path used to build features today, OR (recommended) defers
  the pure-Rust feature extraction to a named follow-up
  ("rust-feature-extraction", sequenced with the NN-representation
  roadmap). **Honest flag:** until that follow-up lands, the
  `rust`-only mode (post-bake-in, post-Python-deletion) cannot
  extract features without the Python state — so **Step 5 (Python
  rules-engine deletion) is gated not only on the bake-in but ALSO on
  rust-feature-extraction landing.** This is a real sequencing edge,
  named here, owner = the umbrella's Step-5 ordering (not a B3
  blocker for Steps 3/4 — the bake-in keeps Python present, so
  features work throughout bake-in).
- **Chance nodes.** Unchanged — `chance_outcomes()` stays `[]`
  (`engine_adapter.py:884-886`); root-level determinization (not
  per-node chance) is the model, same as today.

### 3.5 Mulligan (the pre-game setup boundary)

The London-mulligan loop is in `simulate.setup_game:77-145` (OUTSIDE
the adapter, OUTSIDE `legal_decisions`). B3 design: the setup loop
stays the game-construction boundary. Under `rust`/`rust_shadow`, the
factory builds the Rust state via the surviving
`build_matched_states`/`build_rust_state` loader path
(`cross_engine.py:9516`/`:8895` — the SURVIVING half,
`BRIDGE_VESTIGIALIZATION_PLAN.md` §2.1), and the mulligan decision is
taken by the strategy's `choose_mulligan` (unchanged Python agent
hook) then applied to the Rust state via
`rust_state.mulligan_atomic(...)` (`state_ops_mulligan.rs:486`). This
is a **bounded, named integration point, not an open blocker**: the
mulligan choice is a single pre-game agent call with a tiny decision
space (keep/mull), and Rust's `mulligan_atomic` pymethod already
exists and is cap-correct (`:486`, cap-7 `:198-208`). B3-impl wires
it; no Rust change needed for the mulligan path.

### 3.6 Out of scope of B3 (unchanged, stays Python)

## 4. Parity-safe incremental landing + the shadow-checker bake-in

> **The load-bearing claim:** B3 lands BEHIND the
> `decision_source` flag with `python` as the default. The
> `rust_shadow` mode runs BOTH engines lock-step (Rust drives, Python
> checks) and asserts decision-set + chosen-action + resulting-state
> equality EVERY step, over a production-representative volume,
> BEFORE the atomic SoT flip. Any mismatch is an automatic
> no-flip / rollback signal. The `rust` (Rust-only) mode is enabled
> ONLY after the bake-in closes green.

### 4.1 The shadow-checker (repurposes the existing cross_engine machinery)

In `rust_shadow` mode the provider:

1. Holds BOTH a Rust state (the driver) and a Python state (the
   checker), built matched via `build_matched_states`
   (`cross_engine.py:9516`, the existing matched-state builder).
2. At each decision moment: compute the legal set from
   **Rust** `legal_decisions` (mapped via §3.2) AND from Python
   `legal.legal_actions` (the existing path). **Assert SET EQUALITY**
   on the cast/playland/ability axes (the C1-closed surface) and the
   factored-combat axis (post-G1) — the same equivalence the C1
   Slice-5 probe established (`RUST_LEGAL_DECISIONS_MANA_AWARENESS_
   DESIGN.md` §5 pin 5: *"the post-fix Rust `legal_decisions` cast
   set equals Python's `legal_actions` cast set at each priority
   point"*).
3. The strategy chooses ONE decision from the Rust set. **Apply it
   to BOTH** via the existing `step_both`-shaped mechanism
   (`cross_engine.step_both`, `:10305` — Rust `apply_action` + Python
   `apply_action` + drain + `compare_fields`). **Assert
   `compare_fields == []`** (byte-equal post-step state) AND no
   Python-side `apply_action` invariant raise (the documented C1
   failure mode, `RUST_LEGAL_DECISIONS_MANA_AWARENESS_DESIGN.md`
   §0).
4. ANY set inequality, ANY `compare_fields` divergence, ANY Python
   `apply_action` raise, ANY `fingerprint()` mismatch ⇒ raise loudly
   (no silent fallback — `feedback_no_fallback_hybrids` /
   `feedback_silent_noop_pipelines`: an honest hard failure is the
   real progress signal).

The **exact equivalence assertion** (the bake-in tripwire):

```
LEGAL_SET_EQ : set(map(canon, rust_legal_decisions(pid)))
             == set(map(canon, python_legal_actions(pid)))
               on {PassPriority, PlayLand, CastSpell, ActivateAbility,
                   factored AttackerDecision/BlockerDecision}
CHOSEN_EQ    : the chosen decision encodes to the SAME codec slot
               under both engines' zone views (§3.2)
STATE_EQ     : compare_fields(py_view, rust_view) == []  AND
               rust_state.fingerprint() stable across two
               independent Rust clones from the same pre-state
               (per-seed determinism, BRIDGE_VESTIGIALIZATION_PLAN
               §2.3 J2 invariant)
NO_RAISE     : Python apply_action raised no invariant error
```

`canon` = the canonicalized decision key (kind + zone-position +
variant flags) so set equality is order-independent — the same
canonicalization the C1 asymmetry pin uses
(`tests/test_cross_engine_legal_set_asymmetry.py`, the
characterization/canonicalization/negative-control trio referenced by
`RUST_LEGAL_DECISIONS_MANA_AWARENESS_DESIGN.md` §3.4/§5).

### 4.2 Bake-in exit criterion + rollback

- **Exit criterion** (recommended, matches the umbrella's
  `SOT_FLIP_CUTOVER_PLAN.md` §3 bake-in judgment): `rust_shadow`
  runs divergence-clean (all four assertions hold every step) over
  (i) the C4 bench scale (≥~700 games / ≥7 archetype windows / ≥5
  seed offsets at cap-120, on the flip-candidate commit — this is
  the umbrella's **Step 0** re-run) AND (ii) one real distributed
  `mtg_bot iterate` self-play+eval iteration with zero
  shadow-divergence. Only then is `rust` (Rust-only) enabled.
- **Rollback** is the one-enum revert (§3.1): `decision_source`
  back to `python`. Byte-identical to pre-B3 behavior because the
  Python provider is the unchanged `MtgGameStateAdapter` and the
  flag is read once at game construction. Step 5/6 deletions do NOT
  run until the bake-in closes (the umbrella's reversibility
  invariant, `SOT_FLIP_CUTOVER_PLAN.md` §3).

### 4.3 Why this is genuinely parity-safe (the honest argument)

The `rust_shadow` mode is exactly the existing Python-drives /
Rust-mirrors `step_both` contract **with the driver/checker roles
swapped** — the same `compare_fields`/`fingerprint` machinery, the
same C1 set-equality contract, now used as a *pre-flip gate* instead
of a migration metric. No dev-time fallback wrapper (the failure mode
is a loud raise, not a silent Python fallback —
`feedback_no_fallback_hybrids`). The change is parity-neutral until
the flag is moved off `python`, and the flag is moved off `python`
ONLY after `rust_shadow` proves byte-equality at scale. No large
hidden gap: the three real gaps (G1/G2/G3) are named with scope in
§2.4; G1 is the one true blocker and is a well-shaped sibling Rust
slice (the C1-analog for combat), G2 is a bounded interim-maskable
non-blocker, G3 is an explicitly-accepted C6-fenced strength caveat.
