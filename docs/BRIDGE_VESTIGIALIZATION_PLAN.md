**Strategic framing (the WHY — stated once, not re-derived).** Today
`cross_engine.py` is **bidirectional**:

- **(a) the Python→Rust LOAD path** — a parsed `CardPrinting` →
  `trajectory._printing_to_card_def` → `CardDef` →
  `build_rust_state` → Rust registry. This path **SURVIVES** the
  flip: post-flip the Python parser still produces `CardPrinting`s and
  the loader still feeds Rust. It is the flip-soundness boundary (C6,
  `SOT_FLIP_CUTOVER_PLAN.md:472-480`).
- **(b) the Rust→Python parity-VALIDATION path** — `build_python_state`
  / `_card_def_to_python_printing` (Python-state materializer),
  `build_python_field_view`, `_rust_zone_obj_sig` / `_build_field_view`
  (the Rust→signature reverse projection), `compare_fields`,
  `step_both`'s Python-action replay + dual-engine drain, `walk_both`,
  the `_zone_signature` / `_net_counters` comparators, every
  `*_selector` / `*_side_channel`, and the PROBED tier tooling. This
  entire path exists ONLY to validate Rust against the Python
  source-of-truth. **Once Rust IS the source-of-truth there is no
  Python engine to compare against**, so path (b) becomes dead
  weight — vestigial parity scaffolding.

Retiring (b) **wrong** could silently delete code (a) still needs.
The load-bearing risk is the **shared helpers used by BOTH paths**
(§3.2). This plan's central deliverable is the precise survives /
vestigial / judgment classification and the retirement order whose
invariant guarantees no surviving-path dependency is deleted.

**This is a cleanup payoff, not a parity move.** Bench / parity /

already served its purpose and Python is no longer even a shadow

`cards.rs` line changes.

### 2.3 JUDGMENT — argue both ways, then recommend

Three sub-surfaces are not cleanly vestigial because they have a
**Rust-only** residue that could outlive the Python oracle.

**(J1) The Rust-only halves: `resolve_top_of_stack_rust` (`:10091-10145`),
`deal_combat_damage_rust` (`:10883`), the `*_rust` side-channels, and
`parity_smoke.py`'s Rust-only `run_trajectory_mode` (`:733`) /
`run_multi_seed_mode` (`:849`) (`--mode trajectory` / `multi-seed`
exercise the Rust engine ALONE for determinism).**

- *Argue retire:* they are physically inside the cross-engine module
  and were written as the Rust half of a Rust-vs-Python pair. Cohesion
  argument: deleting "the parity module" wholesale is simpler than
  carving out fragments.
- *Argue keep (as Rust-only regression):* `run_trajectory_mode` /
  `run_multi_seed_mode` are *already* Rust-only (verified
  `parity_smoke.py:10` usage line + `run_rust_engine:437`) — they do
  NOT need a Python oracle. They are a cheap Rust-engine determinism /
  non-crash smoke. Post-flip, "Rust replays the same seed to the same
  bytes" is still a valuable **Rust-only regression** signal (the
  engine must stay deterministic for MCTS reproducibility). Same for
  `resolve_top_of_stack_rust` / `deal_combat_damage_rust` as Rust
  drain primitives a Rust-only regression harness can reuse.
- **Recommendation:** **KEEP (J1), but RELOCATE out of the parity
  module.** Move the Rust-only determinism/smoke modes +
  Rust-drain primitives into a small `rust_regression_smoke` surface
  (a new home; this plan does not create it — it scopes it). Reason:
  their value (deterministic-Rust regression) is real and independent
  of the Python oracle, but leaving them inside a 16k-line module
  90% of which is being deleted is a maintenance trap. The relocation
  is part of the Step-6 slice, gated identically (§4). They are
  **NOT** deleted; they convert from "Rust half of a parity pair" to
  "Rust-only regression".

## 3. The retirement order + the invariant at each step

### 3.1 The single invariant (must hold at every step)

> **LOADER-INTACT INVARIANT.** At every retirement step, the
> Python→Rust load path — `parser → CardPrinting →
> trajectory._printing_to_card_def → CardDef → build_rust_state →
> Rust GameState` — must remain importable and produce a byte-identical
> Rust state for a fixed input deck, AND the umbrella's reversibility
> invariant (`SOT_FLIP_CUTOVER_PLAN.md:388-396`: Python rules engine
> still importable as a shadow checker) must still hold until the
> bake-in closes. No step may delete a symbol the load path or the
> shadow-checker transitively imports.

The objective test for "load path intact": a fixed
`production_deck_to_deckspec` deck → `build_rust_state` → Rust
`fingerprint()` is **unchanged** before vs after each step (a
Rust-only golden, addable by the executable slice — this plan
specifies the gate, §4, not the test).

and the surviving load path. **They cannot be naively deleted.** Each

**#1 — `_card_def_to_python_printing` (`cross_engine.py:9244-9433`).**
