### 2.2 Post-Phase-2 verdict — bridge-CORRECT

Once Phase 2 lands the two rider fields on **both** the CardDef bridge
AND Rust's `CardPrinting`, AND Rust's `cast_creature_warp` debits
`warp_additional_life_cost` from the caster's life, AND Rust's legal
emitter (a) gates the hand warp-cast on `life > life_cost` and (b)
adds a graveyard warp-cast loop mirroring `legal.py:447-463`, AND
Rust's cast pipeline supports a warp-cast-from-graveyard zone arm that
schedules the SAME end-step exile:

> **The life-rider + graveyard-cast warp path is bridge-CORRECT and
> complete for Timeline Culler.** Both engines emit the same action
> set (base + `use_warp=true` from hand when `life > 2`; plus
> `use_warp=true` from graveyard when the card is there and `life >
> 2`), pay the same `warp_cost` + the same 2 life, set
> `spell_warped_this_turn` at the same site, schedule the exile for
> the same end step, and offer the same NORMAL-cost exile-recast on a
> later turn. There is **no residual silent mistranslation** — the
> divergence existed *precisely because* one engine modeled the
> riders and the other didn't; closing it on both sides removes the
> asymmetry entirely. The end-step exile remains the documented
> Phase-1 deterministic `PHASE_END_STEP`-entry sweep, NOT a
> stack-pushed CR-603.7 delayed trigger — Phase 2 does **not** change
> that (see §8 the 2a/2b seam).

**Caveats to flag forward (must hold for the post-Phase-2 claim):**

1. **The Rust `_can_cast` payability divergence is pre-existing and
   orthogonal — but the life gate is NOT a `_can_cast` gate, it is a
   separate predicate Phase 2 MUST mirror.** Phase 1's warp emitter is
   gated on `warp_cost.is_some()` ONLY (mirroring the documented Rust
   "no `_can_cast` payability gate" simplification — the base
   CastSpell emitter is unconditioned on `mana_cost` payability).
   Phase 2's life gate is a *different* axis: Python gates the warp
   emit on `p.life > card.printing.warp_additional_life_cost`
   **independently of mana payability**. Rust DOES model `life`
   (`Player.life`), so the life gate is bridge-correctly portable —
   and it MUST be ported, because without it Rust would offer the
   warp-cast at `life <= 2` while Python would not, a NEW asymmetry
   the base-emitter simplification does not cover. **Phase-2
   decision: gate the Rust warp emit (hand AND graveyard) on
   `player.life as i32 > printing.warp_additional_life_cost as i32`
   — port the life predicate exactly; do NOT port a mana `_can_cast`
   gate (that asymmetry stays as-is, consistent with Phase 1).** For
   Red Tiger Mechan / Bygone Colossus / the Phase-1.5 trio,
   `warp_additional_life_cost == 0`, so `life > 0` is the gate — and
   `life > 0` is always true in any live game (a player at 0 life has
   already lost via SBA), so the new gate is a **no-op for every
   Phase-1/1.5 card** and changes nothing for them. It only bites for
   Timeline Culler (`life > 2`).
2. **The graveyard cast schedules the SAME end-step exile and the
   exile object is re-castable at NORMAL cost, NOT re-warpable from
   the graveyard a second time.** Verified Python: the exile-recast
   path (`actions.py:1488-1510`) always pays `card.printing.mana_cost`
   and clears `warped`. The exile object is in the *exile* zone, not
   the graveyard, so `warp_castable_from_graveyard` does not re-apply
   (the graveyard loop scans `p.graveyard`, not `p.exile`). Rust's
   existing Phase-1 exile-recast branch in `cast_creature`
   (`state_ops_cast.rs:402-493`) already pays `mana_cost` for `warped`
   exile objects — **Phase 2 reuses it unchanged** for the
   post-exile recast of a graveyard-warp-cast Timeline Culler. The
   only new zone arm is graveyard→battlefield at *warp-cast time*.
3. **CR 117.9b — Pay-2-life is part of the warp alternative cost, not
   a separate additional cost a player can decline.** Python pays it
   unconditionally inside the `use_warp` branch (no choice point). The
   Rust mirror MUST debit it unconditionally inside
   `cast_creature_warp` (no decision emitted). There is exactly one
   life-cost value per warp printing; no modal choice.
4. **`state.spell_warped_this_turn` is already a Phase-1 production
   write.** Phase 2's graveyard branch must also set it (Python sets
   it at `actions.py:1457`). This is a positive parity gain (the
   `Effect::ConditionalIfVoid` consumer already reads it via
   `is_void_active`), not a new risk.

## 8. The 2a/2b seam decision — Phase 2 is ONE slice; the delayed-trigger model is a SEPARATE Phase 3

**Phase 2 does NOT split into 2a/2b.** It is one contained Rust slice:
two `CardPrinting` fields + two CardDef fields + a life debit in the
existing `cast_creature_warp` + a graveyard fall-through in the same
primitive + a graveyard legal loop + a life gate on the existing
legal emit + the bidirectional bridge arms + the surgical guardrail
widening (delete 2 clauses) + ~14 pins + the real-EoE probe + the SL
updates. This is comparable in size to Phase 1 (which was a *larger*
slice — new field + new primitive + new sweep + new exile-recast +
2 harness-bug fixes) and smaller than Phase 1's actual landed
footprint, so a 2a/2b split would add merge/sentinel churn for no
risk-reduction benefit. **Recommendation: one Rust round.**

**The genuine seam is Phase 2 ↔ Phase 3 (the delayed-trigger model),
NOT inside Phase 2.** The Phase-1 DESIGN doc §7 sketched "Phase 2 ...
or widen the Phase-1 guardrail to admit the riders once Rust honors
them" and the SL fix-scope note (`SEARCH_LIMITATIONS.md:1840-1843`)
flagged "port Python's `state.delayed_triggers` Vec +
`run_delayed_end_step_triggers` ... a larger follow-on; the
cost-mechanic family's later slices — Phase 2 Timeline Culler — may
motivate it." **Verified analysis: Phase 2 does NOT require the
delayed-trigger port.** Reason: Timeline Culler carries
`triggered_abilities=()` and no LEAVES/DIES observer; the warp-exile
remains the documented deterministic `PHASE_END_STEP`-entry sweep,
bit-equal for `attack_all` exactly as for the Phase-1/1.5 cards (no
card responds to the warp-exile trigger; the bench never holds
priority at end step). The delayed-trigger model is **only** needed
when a future probe puts an instant-speed spell on the stack IN
RESPONSE to the warp-exile trigger — no such card/scenario exists in
the EoE bridge-admitted set. So:

- **Phase 2 (this spec, one Rust round):** the life + graveyard
  riders. Reuses the Phase-1 deterministic sweep unchanged.
- **Phase 3 (a SEPARATE, OPTIONAL, much-later follow-on — NOT a
  warp-card-admit slice):** port `state.delayed_triggers` +
  `run_delayed_end_step_triggers` + a stack-pushed `WarpExileSelf`
  analog to Rust. This admits **0 new cards** (it only changes the
  response-window semantics for a scenario no EoE card reaches); it
  is correctness-completeness work, not leverage work, and should be
  sequenced by the orchestrator only if/when a probe needs the
  response window. It is explicitly OUT of Phase 2's scope.

The seam is therefore clean and stated: **Phase 2 = the two riders,
one slice; the delayed-trigger model is Phase 3, separate, optional,
0-card-leverage, deferred until a response-window probe motivates
it.**
