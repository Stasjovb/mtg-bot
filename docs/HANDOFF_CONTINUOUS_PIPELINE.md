### The orchestrator post-merge cron-resync / fold loop

After each count-shifting Rust merge lands on `main`, the orchestrator
(not the slice agent) runs the **post-merge cron resync**:

1. Rebuild the `.pyd` on `main`, re-run the gate, record the new pass
   count.
2. Run the staleness cron (`scripts/check_audit_coverage_staleness.py`).
3. Apply the **cron-prescribed resync**: bump the sentinel counts,
   regenerate `RUST_EFFECT_COVERAGE.md` / `POOL_PARITY.md`, re-stamp
   `verified_absent_at_commit` on still-genuinely-missing residue
   entries to the new HEAD, fold any newly-closed/reclassified residue
   entries, sync `EOE_PROBE_READINESS_AUDIT.md` /
   `SUBSYSTEM_ROADMAP.md`.
4. Confirm `main` cron exits 0 "in-sync"; tooling tests green.

To avoid the `.pyd`-rebuild race with an in-flight Rust agent,
consecutive Rust merges are **consolidated into ONE deferred resync
pass**, fired only once the Rust slot is free. The resync is part of
the loop, not optional cleanup. **A docs/bench slice must NOT perform
it** — only describe the owed work.
