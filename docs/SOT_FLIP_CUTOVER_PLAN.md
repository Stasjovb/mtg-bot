## 3. Rollback / safety story (unchanged — still correct)

**The reversibility invariant:** Python's rules engine remains
present, importable, and step-for-step runnable as a shadow checker
through the bake-in period; the flip changes only WHICH engine is
authoritative. Do NOT execute Step 5/6 (deletion) until the bake-in
closes green. Rollback is a **one-flag revert of the SoT designation**
(Step 4 is a designation switch, not a deletion).

**Bad-flip detection (tripwire).** During bake-in, Rust is
authoritative but Python runs as a lock-step shadow (the existing
`cross_engine.compare_fields` / `step_both` machinery repurposed —
Rust driver, Python checker). ANY divergence, ANY Python-side
`apply_action` invariant raise (the documented C1 failure mode), or
ANY bench FAIL_DIVERGENCE / FAIL_EXCEPTION on the flipped commit is an
automatic rollback signal. **Constraint on Step 3/4 design:** the
decision-source and SoT-designation switches MUST be a single (or two
coupled) flag(s) so revert is atomic — a half-reverted state must be
unrepresentable.

**Bake-in exit criterion (recommended judgment):** the shadow-checker
runs divergence-clean over a production-representative volume — the
C4 bench scale (≥~700 games / ≥7 windows / ≥5 seeds) PLUS a real
distributed self-play/eval iteration (`mtg_bot iterate`) completing
