# Aura-attachment Phase-1 — implement-ready spec (the static P/T-or-keyword Aura sub-shape S1)

## 0. Why this doc exists

`docs/AURA_ATTACHMENT_SUBSTRATE_PLAN.md` (round-61 N1) established:

- Aura-attachment is the **largest §2-declined multi-round Rust
  substrate audited so far** — strictly larger than warp_cost or
  cost-reduction (it needs an agent-driven cast-target decision + a
  layered continuous-grant-from-attachment + two SBAs + bidirectional
  bridge + a loader predicate, not just a cost field).
- The roadmap's "7 cards / 4 single-gated / 633 single-gate decks"
  Aura row is **disjoint** from the residue Aura cards the strategic
  premise names: Meltstrider's Resolve + Pain for All are
  `blocked_genuinely_missing`, Tractor Beam `blocked_non_effect` —
  **none is in the 7-card row**. Both sets nonetheless converge on the
  same §2 verdict (realizable yield 0 near-term).
- **Aura attachment is carried by NEITHER engine through the bridge.**
  Rust has NO `is_aura` concept anywhere (`grep -rn 'is_aura\|"Aura"\|
  enchant' rust/src/state.rs rust/src/state_ops_cast.rs` → 0 hits —
  verified live), the only `attached_to = Some(...)` sites are the
  Equipment ETB/Equip arms, and an Aura *spell* in Rust currently
  no-ops (it fails `cast_creature`'s Creature-type gate).
- The campaign-confirmed substrate order is **warp (round-63 N1, now)
  → Aura → cost-reduction**. Aura Phase 1 is the next big substrate
  after warp; having its implement-ready spec pipelined now means the
  implementing Rust round won't re-derive the design.

This doc is that substrate's **Phase-1 spec**: the precise CardDef
aura fields, the Rust `CardPrinting` aura field + parse, the Rust
cast-time enchant-target decision (and how Phase 1 handles the
agent-driven long pole via the round-17 Fight / round-51 Monoist
deterministic-bridge-sibling precedent), the Rust Aura-resolution
attach + the layer-7 P/T/keyword grant, the two host-leave SBAs

filter guardrail, the pin plan, the genuine-real-EoE-probe plan, the
per-phase EoE-pool/residue delta, the phase boundaries, and the §2

boundary:** the parser reuses the **Equipment bonus machinery** for
this sub-shape (`cards/base.py:720` —

battlefield scan that Equipment uses (`game.py:972-982` — one loop,
`if source.attached_to != obj.id: continue; eb =
source.printing.equipment_bonuses`). So the *only* new machinery Phase
1 needs on the Rust side that Equipment's shipped arms don't already
have is: (a) recognizing an Aura *spell* (not a creature) at cast,
(b) picking its enchant target at cast (the long pole), (c) stamping
`attached_to` on **Aura spell resolution** (Equipment stamps on ETB
*effect* resolution, a different code path), (d) reading
`equipment_bonuses` through an `attached_to` scan in Rust's effective
P/T (Rust has no such scan today — Equipment's bonus is unmodeled on
the Rust side; this is the substrate's real new continuous-grant
machinery), and (e) the two host-leave SBAs. No control swap, no
layered set-base-PT, no lose-abilities, no triggered effect, no
replacement — those are Phases 2-4.

### 2.1 The pre-substrate state (the divergence Phase 1 closes)

Verified live at `e6f95002`:

- **Python models the full Aura subsystem.** Cast-time
  enchant-target pick (`actions.py:1337-1357` — the
  `if card.printing.is_aura:` block builds the legal host pool by
  `aura_enchant_type` / `aura_yours_only` and calls
  `p.agent.choose_target(state, player_id, legal)`); attach on
  resolution (`actions.py:2720-2758` — re-validates the cast-time
  target, then `card.attached_to = target_obj.id` +
  `apply_aura_static_grants_on_attach`); the
  `equipment_bonuses`/`attached_to`-scan in
  `game._effective_power_toughness` (`game.py:972-982`,
  granted-keyword path 979, P/T path 981-982; the analogous
  keyword-grant scan at `game.py:1122-1124`); the CR-704.5n SBA that
  buries an Aura with no legal host (`turn.py:1327-1358`); the
  host-leave bury (`move_off_battlefield`, `turn.py:216-229`).
- **Rust models NONE of it.** `grep -rn 'is_aura\|"Aura"\|enchant'
  rust/src/state.rs rust/src/state_ops_cast.rs` → **0 hits** (verified
  live). The only `attached_to = Some(...)` sites in all of Rust are
  `state_ops_resolve.rs:8327` (`Effect::AttachToTargetCreatureYouControl`,
  the Equipment-ETB arm) and `:8424`
  (`Effect::EquipToTargetCreatureYouControl`, the Equip-ability arm)
  — both deterministically pick the first eligible creature on the
  controller's bf and are driven from an **Effect resolution**, not
  from spell cast. `Action::CastSpell` (`state_ops_actions.rs:287-334`)
  destructures `use_warp: _` (and ignores every flag) and routes
  unconditionally to `cast_creature` (`state_ops_cast.rs:343`), which
  **returns `Ok(false)` for a non-Creature card** (the
  `if !p.card_types.iter().any(|t| t == "Creature")` gate at
  `state_ops_cast.rs:361`). An Aura is `('Enchantment',)` (subtype
  `Aura`) with `power = None` — so casting an Aura spell in Rust is a
  **silent no-op**: the card never leaves hand, never attaches, never
  grants anything. Rust has no `equipment_bonuses`/`attached_to`
  effective-P/T scan at all (Equipment's bonus is likewise unmodeled
  on the Rust side — `grep -n equipment_bonuses rust/src/*.rs` → 0
  hits). EVERY Rust zone-change path hard-resets `attached_to = None`
  per CR 400.7 (~30 sites in `state_ops_resolve.rs`, e.g. `:1117,
  :1453, :8161, :8250`).
- **The bridge cannot carry it.** `CardDef`
  (`cross_engine.py:106-214`, "only the fields both engines understand
  from a parity standpoint") has **no aura field** — no `is_aura`, no
  `aura_enchant_type`, no `equipment_bonuses`, no `attached_grants_*`.
  `build_rust_state`'s `printing_dict` (`cross_engine.py:8550-8642`)
  emits no aura key; `_card_def_to_python_printing`
  (`cross_engine.py:8842-8971`) constructs a `CardPrinting` with the
  default `subtypes=()` / no `equipment_bonuses`, so the Python side
  is `is_aura == False` ("Aura" not in subtypes — `base.py:1060`).

The drop is **asymmetric and total — it is the object's core
identity, not a rider** (round-61 N1's central §2 finding, reaffirmed
live). The instant an Aura spell would resolve, Python materializes an
attached Aura that pumps its host +N/+M and grants keywords; Rust does
**nothing** (the cast silently no-ops). The post-resolution
battlefield fingerprint mismatches immediately: Python's host is
+2/+2 / has trample; Rust's host is untouched and the Aura is still
in hand. There is **no symmetric-drop bit-equality escape hatch**
(contrast the round-59 shockland / round-39 Ward documented-
simplification precedents: those were riders dropped on *both* bridge
sides, bit-equal under `attack_all`; here the unmodeled thing is the
whole object). The bench's `attack_all` strategy plays creatures and
their pump Auras — it *will* reach the Aura-castable state. **This is
correctly §2-DECLINED today** (round-61 N1's verdict, reaffirmed
against the live tree).

### 2.2 Post-Phase-1 verdict — bridge-CORRECT for S1

Once Phase 1 lands the aura representation on **both** the CardDef
bridge AND Rust, AND Rust's `legal_actions` emits the Aura cast under
the same condition Python does, AND Rust's Aura-spell resolution
stamps `attached_to` + applies the `equipment_bonuses` layer-7 grant
through an `attached_to` scan, AND both engines bury the Aura on
host-leave with byte-equal timing:

> **The static `equipment_bonuses` Aura path is bridge-CORRECT and
> complete for Frantic Strength** (and for Shardmage's Rescue as the
> documented conditional-hexproof-dropped simplification). Both
> engines emit the same Aura CastSpell action when a legal host
> exists, attach to the **same host** (the deterministic-bridge-
> sibling pick — §3.4), grant the **same** effective P/T + keyword on
> the host, and bury the Aura at the **same** SBA tick when the host
> leaves. There is no residual silent mistranslation for the flat-
> bonus shape — the divergence existed *precisely because* one engine
> modeled Aura attachment and the other didn't; closing it on both
> sides for the flat-bonus profile removes the asymmetry entirely.

**Caveats to flag forward (must hold for the post-Phase-1 claim):**

1. **The agent-driven enchant-target decision is the long pole and
   Phase 1 does NOT build a cross-engine agent-decision substrate.**
   It follows the round-17 Fight / round-51 Monoist deterministic-
   bridge-sibling precedent **exactly** (`SEARCH_LIMITATIONS.md:2036-
   2068`): Rust's Aura-resolution attach picks the **first eligible
   host in ETB-timestamp order** on the legal pool (deterministic),
   and the genuine real-EoE probe drives the real Python class
   **shim-constrained** (`_PickFirstControlledCreatureAgent` /
   `_PickFirstLegalTargetAgent` from `tests/parity/_picker_shims.py`)
   so Python's agent-driven `choose_target` equals Rust's
   deterministic scan **in the single-eligible-host scenario**. The
   loader admit is **declined for the ambiguous case** (≥2 legal
   hosts where an agent would rationally pick a non-first host —
   that's a strategy divergence, not just representational): the
   Phase-1 filter guardrail `_printing_is_bridge_static_aura` admits
   the card structurally, but the genuine probe + the bench harness
   are constructed so the bench only reaches the
   single-eligible-host shape (Frantic Strength / Shardmage's Rescue
   have **0 EoE decks** — there is no real archetype to drive, so the
   ambiguous multi-host case never arises in a real bench game; see
   §5). When a future round lands the shared cross-engine agent-driven
   single-target decision substrate (the Monoist/Fight long pole),
   Rust's Aura attach gains a target-carrying variant + decision
   callback and the deterministic scan becomes the synthetic-probe
   substrate only (same trajectory as the Fight-Aura follow-up). **The
   spec is written so Phase 1 ships the deterministic sibling, not the
   agent substrate** — that keeps Phase 1 to one Rust round.
2. **Shardmage's Rescue's conditional hexproof MUST be dropped
   symmetrically or the card stays Phase-2+.** Its
   `entered_this_turn`-gated layered hexproof grant is a conditional
   continuous effect Rust has no analogue for. Phase 1's two options:
   (a) admit Shardmage's Rescue with the conditional hexproof dropped
   on **both** bridge sides (the round-59 shockland symmetric-drop
   precedent — bit-equal under `attack_all`, which never targets the
   enchanted creature so hexproof never matters; SL entry mandatory,
   §3.8), OR (b) the guardrail rejects any Aura with a conditional
   layered grant and Phase 1 ships **Frantic Strength only**
   (+1 card). **Recommended: (b) — Frantic Strength only.** Shardmage
   carries `aura_yours_only` (a *different* legal-pool restriction
   than Frantic's plain "Enchant creature") AND the conditional grant;
   admitting it adds two orthogonal risk surfaces to the minimal
   slice for +0 decks (0 EoE decks either way). Ship the cleanest
   possible Phase 1; Shardmage's Rescue + `aura_yours_only` +
   conditional-grant fold into Phase 2 with Duskmourn's Domination's
   layered-grant work. The guardrail in §3.7 implements (b); §3.8's SL
   note records the deferral.
3. **`attached_to` becomes a real production write on Rust for Auras.**
   Today it is Equipment-ETB-only. Phase 1's Aura-resolution arm sets
   it from the cast pipeline — a *positive* parity gain (the shipped-
   but-fizzling `TapEnchantedPermanent` Tractor-Beam Effect, which
   reads `source.attached_to`, starts working for Auras too once Phase
   1 sets it — but Tractor Beam stays loader-declined until Phase 3
   because of its control-swap composition; Phase 1 only changes the
   field, not Tractor Beam's admit status). The implementing agent
   must update the relevant SL pin (§3.8).

### 3.2 CardDef aura bridge fields

**File:** `src/mtg_bot/parity/cross_engine.py`, the `CardDef`
dataclass (declared at line 107; append the new fields after
`token_activated_abilities: tuple[dict, ...] = ()` at line 214 — same

```python

    # (`cards/base.py:720`). `is_aura=False` (back-compat default;
    # every pre-Phase-1 CardDef omits these, build_rust_state then
    # omits the aura keys and the Rust parser maps the absence to a
    # non-aura printing). Phase 1 carries ONLY the flat-bonus,
    # enchant-creature, no-yours-only, no-conditional-grant shape; the
    # filter guardrail `_printing_is_bridge_static_aura` positively

    # `aura_yours_only` / conditional layered grants / any triggered

    # the scalar enchant_type keep CardDef frozen-hashable and match
    # the existing flat-field convention (no nested ManaCost/object).

    aura_enchant_type: str = "creature"   # Phase 1: always "creature"

    aura_toughness_bonus: int = 0
```

**Design note (verified against the live `equipment_bonuses` codec):**
Python represents the Aura's continuous grant as the SAME
`(power_bonus, toughness_bonus, granted_keywords)` triple Equipment
uses (`base.py:720`; `make_aura` builds it at `base.py:1529-1531`).
CardDef flattens it to three scalar fields (mirroring how
`mana_cost_generic`/`mana_cost_colored` flatten a `ManaCost` rather
than nesting the object — keeps the frozen dataclass hashable and
matches the existing field convention). `is_aura: bool` disambiguates
"not an aura" from "an aura granting +0/+0 with no keywords" (Python's
semantic is `"Aura" in subtypes`, which a `(0,0,())` triple alone
could not express). `aura_enchant_type` is carried (scalar str) for
forward-compat with Phase 4's artifact-enchant Auras even though Phase
1 only ever sets `"creature"` — the Rust parser + bridge thread it now
so Phase 4 doesn't re-plumb it.

### 3.4 Rust `legal_actions` — emit the Aura CastSpell when a legal host exists

**File:** `rust/src/state_ops_legal.rs`.

Python emits the Aura CastSpell only when a legal enchant host exists
(`actions.py:1354` `if legal:` — if no host, the Aura is uncastable;
mirrors CR 601.2c / 303.4: an Aura spell requires a legal target on
the stack). Rust's sorcery-speed CastSpell emitter
(`state_ops_legal.rs:994-1022`) currently emits `cast_spell_dict` for
every non-Land non-Instant non-flash hand card regardless of
castability (the documented "Rust has no `_can_cast` payability gate"
simplification — module docstring lines 73-119). **Phase-1 decision:
gate the Aura CastSpell on legal-host-existence** (NOT on mana
payability — that stays the documented base-emitter simplification),
because host-existence is the Aura's *targeting* legality, which
Python enforces at the emitter and which has no symmetric base-emitter
